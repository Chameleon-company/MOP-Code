Smart Street Lighting Efficiency¶

Use Case: Project 30 – Smart Street Lighting Efficiency
Team: Binul Bijo and Kliona Kennet
Purpose: This notebook demonstrates how streetlight, traffic, and pedestrian datasets can be combined to identify lighting efficiency patterns and generate practical recommendations.

Scenario¶

Cities often operate streetlights using static schedules, even though traffic and pedestrian activity changes across the day. This can cause some periods to be over-lit, where lighting is higher than needed, and other periods to be under-lit, where high activity may require stronger lighting support.

This use case explores how real Melbourne urban datasets can support smarter lighting decisions by analysing hourly activity patterns.

What this use case demonstrates¶

By the end of this notebook, the project demonstrates:

  • Loading and inspecting three project datasets
  • Cleaning streetlight, traffic, and pedestrian data
  • Creating hourly traffic and pedestrian activity measures
  • Integrating datasets using a time-based approach
  • Creating a weighted demand score
  • Classifying lighting conditions as over-lit, efficient, or under-lit
  • Generating recommendation analysis for smart lighting decisions
  • Saving final outputs and visualisations as project evidence

Datasets used¶

This use case uses three datasets:

  1. Street Light Locations dataset – provides lighting infrastructure information, including location and emitted lux levels.
  2. Traffic Flow dataset – provides vehicle movement data that is used to calculate hourly traffic activity.
  3. Pedestrian Counting dataset – provides hourly pedestrian counts from Melbourne sensors.

Because the datasets do not share a perfect common spatial key, the integration is performed using an hourly activity approach. This is suitable for showing how lighting demand changes across the day.

10. Demand score calculation¶

A demand score is created to represent overall urban activity for each hour. Traffic is given a 60% weight and pedestrian activity is given a 40% weight. This reflects the assumption that vehicle movement has a slightly higher influence on road lighting demand, while pedestrian movement remains important for safety.

In [17]:
merged_activity['demand_score'] = (
    merged_activity['traffic_level'] * 0.6 +
    merged_activity['pedestrian_level'] * 0.4
)

11. Efficiency classification¶

The demand score is split into three ranges using quantiles. Low-demand hours are classified as over-lit, high-demand hours are classified as under-lit, and middle-demand hours are classified as efficient. This makes the classification data-driven instead of manually choosing fixed thresholds.

In [18]:
low_threshold = merged_activity['demand_score'].quantile(0.33)
high_threshold = merged_activity['demand_score'].quantile(0.66)
print("\nLow threshold:", low_threshold)
print("High threshold:", high_threshold)
def classify(row):
    if row['demand_score'] >= high_threshold:
        return "under-lit"
    elif row['demand_score'] <= low_threshold:
        return "over-lit"
    else:
        return "efficient"
merged_activity['efficiency'] = merged_activity.apply(classify, axis=1)

12. Recommendation analysis¶

The recommendation logic converts each efficiency category into a practical action. Under-lit hours suggest increasing lighting, over-lit hours suggest reducing lighting, and efficient hours suggest maintaining the current setting.

In [19]:
def recommend(row):
    if row['efficiency'] == "under-lit":
        return "Increase lighting during peak activity hours"
    elif row['efficiency'] == "over-lit":
        return "Reduce lighting during low activity hours"
    else:
        return "Lighting is optimal for current activity"
merged_activity['recommendation'] = merged_activity.apply(recommend, axis=1)

Limitations and future improvements¶

  • The datasets do not share a perfect location-based key, so this version uses hourly integration.
  • Future work can improve the model by linking streetlights to nearby traffic or pedestrian sensors using spatial nearest-neighbour methods.
  • The 60/40 weighting can be refined using lighting standards, expert input, or validation data.
  • A dashboard or map-based view can be added to make the final output more interactive.
